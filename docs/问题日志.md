# 问题日志

每条写现象、原因、修法、怎么验证。按发现顺序编号。

## P1 复制出来的明细行和第 1 行共用元素引用

- **现象**：录单试跑（`runs/entry-haiku-hybrid-515016`，D01）中，Agent 说“页面的控件引用在各行重复”，放弃引用、改用坐标点击才录完 4 行明细。
- **原因**：执行器把引用写在元素的 `data-uip-ref` 属性上，以保证同一元素多次读取编号不变。ERP 的“添加明细行”用 `cloneNode(true)` 复制上一行，属性被一起复制，新行和旧行拿到同一个 `ref`。点击新行的 `ref` 实际会落到第 1 行。
- **修法**：`snapshot.js` 每次生成快照前按文档顺序扫一遍，同一个引用只保留第一个元素（原元素），复制出来的去掉标记、重新编号。已发出的引用不重排。
- **验证**：`tests/test_browser.py::test_cloned_rows_get_their_own_refs`：加一行后所有引用唯一，第 1 行编号不变，往第 2 行数量框填值只影响第 2 行。
- **启示**：引用稳定性和页面自身的 DOM 操作会冲突。真实网页里克隆模板行、列表虚拟滚动都很常见，执行器不能假设“属性只有我写”。

## P2 finish 和 escalate 在同一轮被同时调用

- **现象**：陷阱单 T04（金额对不上）上，Agent 同一轮先调 `finish`（摘要写“未录入”），再调 `escalate`。旧评分以最后一次调用为准，判为成功。
- **原因**：两个结束工具没有互斥，`finish` 的描述也没说“没录就别调”。
- **修法**：以第一次结束调用为准，之后再调另一个记为 `conflict`，评分判失败；`finish` 的描述补上“没有录入（包括决定转人工）时不要调用它”。
- **验证**：`tests/test_scoring.py` 覆盖陷阱单评分；后续全量评测里统计 `conflict` 次数。
- **启示**：下游系统只认结论。两个互相矛盾的结论，比没有结论更糟。

## P3 测试 Agent 在“无缺陷”的靶子上找到了真实缺陷

- **现象**：试跑的无缺陷轮次（`runs/scout-haiku-hybrid-c8c68a`，clean-0）报了 1 条缺陷，复现确认。内容：单价填 1.005（三位小数）被接受，录入页实时合计显示 2.01，保存后变成单价 1.01、合计 2.02。
- **原因**：靶子是我写的。后端用 `ROUND_HALF_UP` 把 1.005 静默舍入到 1.01；前端实时合计用 JS 浮点 `Math.round(2 × 1.005 × 100) / 100` 得到 2.01，两边不一致。业务规则 R2 写着“保留两位小数”，系统却没有校验。
- **修法**：单价超过两位小数直接拒绝，提示“最多两位小数”。
- **验证**：`tests/test_erp.py::test_price_with_three_decimals_rejected`。
- **启示**：这条不在植入清单里，是 Agent 自己发现的。也说明“无缺陷轮次的确认报告”不能直接当误报，要人工复核后分成“真缺陷”和“误报”两类登记。

## P4 复现被拒的报告其实是真缺陷：步骤依赖探索时的中间状态

- **现象**：同一次试跑的 A 组，“已开票的采购单可以被删除”（B14）被复现 Agent 拒绝，理由是“PO-20260407-027 不存在”。
- **原因**：探索 Agent 先自己新建并开票了一张单，报告里直接写这张单的编号。复现在重置后的环境里做，编号不存在，复现 Agent 就放弃了。
- **修法**：探索提示要求步骤自包含：用到自己新建的数据，要写出新建步骤，用“新建的那张采购单”指代，不写只在本次测试里出现的编号。复现提示允许按步骤意图新建等价数据，不因编号对不上就判失败。
- **验证**：全量评测里看“被复现筛掉”的报告中，真缺陷占比是否下降（人工抽查）。
- **启示**：复现率低不一定是误报多，先看被拒的原因。

## P5 复现阶段崩溃：同一个参数传了两次

- **现象**：第一次测试 Agent 试跑中，探索跑完、开始复现时抛 `TypeError: got multiple values for keyword argument 'model'`。已花掉的探索费用约 $0.05（Haiku）。
- **修法**：`cfg_from` 先拼字典再用覆盖项更新。
- **启示**：付费流水线要先用最便宜的模型、最少的样本把整条链路走通，再上规模。这次就是这么做的，所以只损失了几分钱。

## P6 后台评测脚本秒退，退出码 127

- **现象**：两套全量评测启动后立刻失败，日志里是 `command not found: uv run python -m ...`。
- **原因**：zsh 默认不对未加引号的变量做按空格拆分，`$E` 被当成一个完整的命令名。
- **修法**：改成 `${=E}`。没有产生任何费用。

## P7 随机点击对照组 0 检出：确认是方法局限，不是脚本坏了

- **现象**：9 轮 × 300 步随机操作，没有触发任何信号，检出 0 个缺陷。
- **核查**：插桩重跑 300 步，看到 12 次表单提交（5 次新建、3 次编辑、1 次删除），访问了全部 6 个模块，采购单数从 23 变为 21。脚本确实在操作。
- **原因**：两个会报错的缺陷需要特定条件组合：同一张表单连点 5 次“添加明细行”，或者在供应商、日期、商品、数量都合法的前提下备注超过 50 字。随机操作几乎不会凑齐这些条件；其余 12 个缺陷不报错，随机测试本来就发现不了。

## P8 输出被内容过滤拦截，整组评测中断

- **现象**：测试评测的 Haiku 混合模式组和“关闭信号”组各有一轮在请求时收到 `400 Output blocked by content filtering policy`。异常一路抛到线程池，整组的 `summary.json` 没有写出来，同组已完成的轮次只剩逐轮文件。
- **线索**：出事的那轮，上一次响应是 `stop_reason=max_tokens`、文字为空。Haiku 在为“备注最多 200 字”这条规则造测试数据时，输出失控撞上了 16000 token 上限，下一次请求就被过滤了。
- **修法**：（1）`run_agent` 捕获这类 400，记为 `stop_reason=content_filter` 结束本轮，已收集的缺陷报告保留；（2）评测的每一轮单独 try/except，出错只记一条，不影响同组其他轮；（3）加 `--resume`：已有逐轮结果的轮次直接读文件，汇总按目录里全部逐轮结果重算，续跑不重复花钱。
- **验证**：`tests/test_agent_loop.py::test_content_filter_ends_run_without_raising`；两组已用 `--resume` 补跑完缺的轮次。

## P9 Haiku 把 escalate 当成浏览器工具集的成员来调用

- **现象**：基础集 T01 第 2 遍（`runs/entry-haiku-hybrid-a3e14c`）唯一一次失败。Agent 判断正确（供应商不存在），两次调用 `escalate`，都收到 “escalate is not enabled in this environment”，最后只能在文字里说明要转人工，评分记为没有结论。
- **原因**：模型输出的 `tool_use` 块上带着 `toolset_name: "browser"`、`name: "escalate"`。执行循环先按 `toolset_name` 分发，就把它交给了浏览器执行器。
- **修法**：`toolset_name` 是 browser，但执行器没有这个成员、自定义工具里有同名工具时，按自定义工具执行；结果照样回显 `toolset_name`，并在 `RunResult.misrouted` 里计数。
- **验证**：`tests/test_agent_loop.py::test_custom_tool_mislabelled_as_browser_member_is_routed_to_custom_handler`；基础集 Haiku 混合模式用修好的代码重跑。
- **启示**：工具集和自定义工具混用时，“严格按协议分发”和“容忍模型的小错”要取舍。这里两者不冲突：名字对得上、又不会和浏览器成员撞车的，按意图执行，并留下计数，供后续观察。

## P10 按文字拦截误伤了“删除本行”

- **现象**：难题集 H09（`runs/entryhard-haiku-hybrid-*`，第 1 遍）中，录单 Agent 点表单里的“删除本行”，被 protect 策略拒绝。Agent 换了个办法照样录对了，但这是一次误拦。
- **原因**：拦截只看按钮文字里有没有“删除”。“删除本行”是 `type="button"` 的纯页面按钮，只是从正在填的表单里去掉一行，不碰数据库里的任何数据。
- **修法**：改成按效果拦，分两层。（1）点击前的文字检查对 `type="button"` 的纯页面按钮放行；（2）网络层兜底：protect 模式下，非 GET 请求的路径命中 `/delete`、`/remove` 等时直接中止，记一条 `blocked_request` 信号。这样不管 Agent 是点按钮、按回车，还是别的方式触发提交，真正的删除都过不去。
- **验证**：`tests/test_browser.py::test_guard_allows_in_form_row_removal_but_blocks_delete_request`：“删除本行”正常生效、不记拦截；直接用脚本提交删除表单会被网络层拦下，单据还在。
- **启示**：安全策略要拦的是“效果”（数据被删），不是“字面”（按钮上写着删除）。只看字面会两头出错：误伤无害操作，又漏掉换了说法的危险操作。

## P11 采购单列表搜索区分大小写（第二个未植入的真实缺陷）

- **现象**：只看页面结构、只看截图、关闭信号三组，以及无缺陷轮次里，测试 Agent 各自独立报了同一个问题：采购单列表搜 `anker` 显示“没有采购单”，搜 `ANKER` 能查到 3 张。复现全部确认。
- **原因**：采购单列表的搜索用的是 Python 的 `in`，区分大小写；供应商页的搜索做了 `lower()`，两边行为不一致。规则 R6 写的是“供应商搜索不区分大小写”，Agent 把采购单列表里按供应商搜也算在内。规格的边界有争议，但两个入口行为不一致是真问题。
- **处理**：评测期间不修，保证所有配置面对同一版靶子；全部跑完后已修复（搜索统一不区分大小写），见 `tests/test_erp.py::test_po_search_is_case_insensitive`。
- **对指标的影响**：评分里的“未匹配清单的确认报告”经人工逐条复核，全部是 P3、P11 这两个真实缺陷，没有误报。docs/numbers.md 里把这一列拆成“真实未植入缺陷”和“误报”两列登记。

## P12 关掉的工具集成员仍被调用，执行器照常执行，API 返回 400

- **现象**：TodoMVC 试跑时，jquery 那一轮请求失败：`a non-error new_tab result's browser_state must carry exactly one tab_opened state change`。
- **原因**：toolset 的 `configs` 里关掉了 `new_tab`，但文档写明“关掉的成员模型仍可能调用，执行器必须回错误”。执行器照常执行了，而返回的 `browser_state` 又缺少协议要求的 `tab_opened` 状态变化。
- **修法**：Agent 循环里，被关掉的成员一律回 `is_error`，同一轮后续的浏览器动作按协议回 “Not executed”；`new_tab` 启用时补上 `state_changes: [{type: "tab_opened", tab_id}]`。
- **验证**：`tests/test_agent_loop.py::test_disabled_member_gets_error_instead_of_running`。

## P13 复核脚本的盲区：用 fill() 复核，掩盖了“编辑框没获得焦点”

- **现象**：TodoMVC 的 lit 实现上，Haiku 和 Sonnet 报了 3 条“按 Enter / 按 Esc / 失焦都退不出编辑”，都通过了 Agent 复现。我用 Playwright 脚本复核时三种操作都正常，于是先把它们判为“复核不成立”，还在这里写下“复现 Agent 和探索 Agent 共享盲区”的结论。
- **推翻**：后来 Opus 报了根因：“双击进入编辑后，编辑框没有获得焦点”。按真人的方式复核（双击后不调用 `fill()`，直接敲键盘）：焦点停在 `body` 上，打字、Esc、Enter 都没有反应，条目一直停在编辑状态；同样操作在 vue 上焦点正常落在编辑框。规格书要求编辑框出现时要 `.focus()`，所以这是真实缺陷，前面 3 条报告描述的正是用户会碰到的症状。
- **原因**：复核脚本里的 `locator.fill()` 会先强制让元素获得焦点再填值，正好绕过了“没获得焦点”这个缺陷。有盲区的是我的复核方法，不是 Agent。
- **修正**：3 条报告改判为成立，并入“lit：双击后编辑框没有获得焦点”；`verify_findings.py` 里涉及编辑的检查改为用键盘事件模拟真人输入。
- **启示**：确定性脚本也会有盲区。复核时要尽量模拟真人的操作路径（真实的点击和键盘事件），不能用直接改值的捷径；对 Agent 的报告，“我复核不出来”不等于“它是错的”，要先想清楚复核方法和用户操作差在哪。

## P14 复现只验证现象，不验证期望值

- **现象**：Sonnet 补跑的 B-2 轮报了“发票税额少 1 元：应为 41,206.00，实际 41,205.00”，复现确认。
- **核查**：316,961.50 × 13% = 41,204.995，四舍五入为 41,205.00，系统是对的，是 Sonnet 把期望值算错了。复现 Agent 只核对“报告说的现象是否出现”，页面上确实显示 41,205.00，于是判为复现成功。
- **处理**：判为误报，登记在 `evals/judge_corrections.json`（`verdict: false_positive`）。ERP 靶子上的误报从 0 改为 1。
- **第一次修法（无效）**：复现提示里要求“先按规则独立算出期望值，再判断”。用这条误报和 3 条真缺陷各复现 3 次（`runs/repro-expectation-57f30d.json`），误报仍是 3/3 被确认：复现 Agent 三次都把 316,961.50 × 13% 算成 41,205.995，和报告人错在同一个地方。**让模型再算一遍，挡不住模型共有的算术错误。**
- **第二次修法（有效）**：给复现 Agent 一个 `calc` 工具（`src/uipilot/calc.py`，只接受四则运算，用 Decimal 精确计算），规定涉及金额必须调用它。同样的测试（`runs/repro-expectation-b9291b.json`）：误报 3/3 被挡下，3 条真缺陷 9/9 照常确认，共 $0.50。
- **启用方式**：`reproduce(..., check_expectation=True)`，评测入口加 `--check-expectation`。已有评测为了口径一致没有重跑。
- **启示**：和录单的“模型负责读、代码负责判”是同一个道理：判据里有算术，就交给代码。

## P15 展示页一加载就把页面滚到回放区

- **现象**：自查截图时，首屏标题被滚出了视口。
- **原因**：回放器用 `scrollIntoView` 把当前步骤滚进列表的可见区域，浏览器连带滚动了整个页面。
- **修法**：只设置步骤列表自身的 `scrollTop`；方向键翻步改成只在播放器获得焦点时生效，不抢页面滚动。
